### 1.1 反馈语气规则

| 场景 | 允许语气 | 禁止语气 |

| 一般知识答错 | "这题有点绕，我们再看一眼。" | "你失败了""能力不足" |

## 2. Web3 通识课程（完整 3 章）

**学习目标**：理解账户、钱包、交易和基础安全，能够判断常见风险。

### 2.1 第 1 章：区块链、账户与地址（认识/破冰）

- **章节目标**：学完你会知道，链上的账本为什么改不了、钱包地址是不是秘密。
- **正文**（约 220 字）：
  区块链可以理解成一本所有人都能看、但没人能私自涂改的账本。每一笔交易被确认后，会通过密码学哈希和前一笔记录"锁"在一起——改动其中一笔，后面所有记录都会对不上，这就是"不可篡改"的来源。你的钱包地址就像这本账本上的一个身份编号，任何人都可以查到这个编号做过什么交易，但光凭这个编号，没有人能动你的资产。真正决定"谁能操作这个地址"的，是只有你自己保管的私钥/助记词，这个我们会在第 3 章详细讲。
- **关键术语**：区块链、钱包地址、不可篡改。
- **例子**：你可以把自己的钱包地址发给朋友收款，就像告诉别人银行卡号一样，别人能看到卡号但拿不走钱。
- **风险/注意事项**：地址公开不等于不安全，但也不代表"分享什么都没关系"——真正要保密的东西在后面章节。
- **知识卡**：
  1. 是什么：区块链是一本公开、不可篡改的账本。
  2. 为什么要知道：理解"公开可查"和"资产安全"是两回事，是后面所有安全判断的基础。
  3. 用户会看到什么：区块浏览器上任意地址的历史交易记录。
  4. 哪些动作会改变状态：只有真正发起交易（写入操作）才会改变账本，单纯查看不会。
  5. 操作前检查什么：本章无需操作，只需理解概念。

**挑战**（判断题 ×1）

- 场景：农场的老邻居阿伯路过，问你——"听说这链上的账本，谁都改不了？"
- 题目：区块链上的交易记录一旦被网络确认，任何单方都无法私自修改。
- 答案：正确
- 答对反馈："没错，这片地的账本，谁也偷偷改不了。"
- 答错反馈："没关系，我们再想想：如果账本能被一个人偷偷改，那大家还会信这本账吗？"

### 2.2 第 2 章：读取、签名与交易（熟练/巩固）

- **章节目标**：学完你会分辨，哪些操作不用签名、一笔交易是怎么从发起到确认的。
- **正文**（约 260 字）：
  链上操作分两种：读取和写入。查询余额、查看别人的交易记录，这些都是"读取"——你只是在看账本上已经写好的内容，不会改变任何东西，所以不需要签名，也不花 Gas。但转账、种植、兑换这类会真正改变账本状态的操作，属于"写入"，必须由你签名确认，系统才会执行。一笔写入交易的完整流程是：你签名发起 → 交易广播到网络 → 被打包进区块 → 网络确认完成。中间的"签名"就是你对这笔操作的授权，没有它，网络无从知道这是你本人同意的操作。
- **关键术语**：读取操作、写入操作、签名、Gas。
- **例子**：查看自己钱包里有多少 USDC 是读取，不用签名；把 100 USDC 转给朋友是写入，需要签名确认。
- **风险/注意事项**：签名意味着"我同意这件事发生"，不要在没看清内容的情况下随手签名——这一点会在第 3 章重点展开。
- **知识卡**：
  1. 是什么：读取是查看链上数据，写入是改变链上数据并需要签名授权。
  2. 为什么要知道：分清两者才能判断"这一步到底需不需要我确认"。
  3. 用户会看到什么：读取时界面直接显示结果；写入时钱包会弹出签名请求。
  4. 哪些动作会改变状态：只有写入操作（转账、种植、兑换等）会改变链上状态。
  5. 操作前检查什么：签名前确认这笔操作的内容和对象是你真正想做的事。

**挑战**（两项选择 ×1 + 简单排序 ×1）

**两项选择**
- 场景：你在仓库门口，一会儿"看看有多少存货"，一会儿"往外发货"。
- 题目：只是看看自己仓库里有多少 USDC，需要你签字确认吗？
  - A. 需要　　B. 不需要
- 答案：B
- 答对反馈："对，看看货架而已，不用签字，仓库的东西也不会因为你看一眼就变化。"
- 答错反馈："再想想：这一步有没有真的改变你钱包里的东西？"

**简单排序**
- 场景：你要给隔壁农场寄一批货，中间要经过几道手续。
- 题目：把寄货流程排个顺序：① 货物被打包上车（打包进区块）② 你签字确认要寄（用户签名）③ 快递员把消息传出去（交易广播）④ 对方农场确认收货（交易确认完成）
- 答案：② → ③ → ① → ④
- 提示 1（第一次答错后）："先想想，是先签字，还是先打包？得有人先说'我要寄'才行。"
- 提示 2（第二次答错后）："快递员得先知道有这单货，才能安排打包，对不对？"
- 答对反馈："顺序对啦，这就是一笔交易从发起到完成的完整旅程。"

### 2.3 第 3 章：私钥、助记词与签名风险（认真收尾 · 严肃模式）

> 本章为安全章节，Agent 引导语固定为："这一步涉及账户或资产安全，我陪你认真确认一遍。"不使用场景软化、不使用轻松语气。

- **章节目标**：学完你会知道，什么绝对不能分享、什么样的签名请求要提高警惕。
- **正文**（约 240 字）：
  钱包地址是公开的门牌号，但私钥和助记词是打开这个门牌号里所有资产的万能钥匙——一旦泄露，任何人都可以不经过你直接转走全部资产，且这个操作无法撤销。任何自称"官方"的活动、客服或空投，只要要求你输入助记词或私钥，都应该被立即判定为风险，无论包装得多正式、金额听起来多有吸引力。除此之外，签名请求也要看清楚内容再确认——"盲签"（看不懂内容就点确认）是另一类常见风险，尤其是陌生 DApp 弹出的授权请求。
- **关键术语**：私钥、助记词、盲签。
- **例子**：银行不会打电话问你要银行卡密码，同理，任何 Web3 项目方也不会需要你的助记词才能给你发奖励。
- **风险/注意事项**：本章知识点是全课程的安全底线，答错时不使用轻松文案，必须让用户明确说出风险信号。
- **知识卡**：
  1. 是什么：私钥/助记词是资产的完全控制权，签名是对单次操作的授权。
  2. 为什么要知道：这是链上资产被盗最主要的两类原因。
  3. 用户会看到什么：钓鱼信息通常伪装成官方活动、客服私信；风险签名通常是陌生 DApp 的弹窗请求。
  4. 哪些动作会改变状态：交出助记词=完全失去控制权；确认一个看不懂的签名=可能授权他人转走资产。
  5. 操作前检查什么：任何索要助记词的请求直接拒绝；任何签名请求先看清楚在授权什么。

**挑战**（风险场景判断 ×2）

**第 1 题**
- 题目：你收到一条私信，对方说"官方空投活动，输入助记词即可领取奖励"，你应该怎么做？
  - A. 按要求输入助记词，尽快领取　　B. 不提供助记词，任何官方渠道都不会索要助记词
- 答案：B
- 反馈：答对——"守住了，这是最常见的骗术之一，你的判断是对的。"答错——不使用软化文案，直接说明后果："交出助记词等于把资产的完全控制权交给对方，这类操作无法撤销。任何要求提供助记词的请求，无论包装成什么，都必须拒绝。"

**第 2 题**
- 题目：一个陌生网站弹出一个你完全看不懂内容的签名请求，还在不断提示你"尽快确认，名额有限"，你应该？
  - A. 既然打开了就先签了看看，反正可以后悔　　B. 不确认，先弄清楚这个签名到底在授权什么，必要时直接关闭页面
- 答案：B
- 反馈：答对——"对，看不懂内容就点确认，风险都在这一步发生。你的处理是对的。"答错——"签名一旦确认就无法撤销，'催促你尽快操作'本身就是常见的施压话术。看不懂就不签，永远是更安全的选择。"

最终验证要点（对应 v3.5 §5.2）：能解释地址与私钥的区别；能说明读取公开余额为什么不需要签名；能说出签名前需要检查的内容。

## 3. Monad 基础课程（完整 3 章）

**学习目标**：理解 Monad 网络的基本使用方式，能够读取和识别公开链上状态。

### 3.1 第 1 章：Monad 与 EVM（认识/破冰）

- **章节目标**：学完你会知道，Monad 和以太坊的开发生态是什么关系。
- **正文**（约 200 字）：
  Monad 兼容 EVM（以太坊虚拟机），这意味着原本部署在以太坊上的智能合约，通常只需少量甚至无需修改就能部署到 Monad 上，开发者熟悉的工具和代码可以直接复用。这也是 Monad 生态能够快速积累应用的关键原因之一。但"兼容"不代表"完全相同"——网络地址、RPC 节点、浏览器都是 Monad 独立的一套，不能和以太坊的混用。
- **关键术语**：EVM 兼容、RPC。
- **例子**：一个原本跑在以太坊上的兑换合约，开发者稍作调整就能部署到 Monad，这也是为什么 Monad 上很快就出现了很多熟悉的应用类型。
- **风险/注意事项**："兼容"只是开发层面的便利，操作时依然要核对自己连接的是不是 Monad 网络。
- **知识卡**：
  1. 是什么：Monad 是一条兼容 EVM 的高性能公链。
  2. 为什么要知道：理解这一点能解释"为什么 Monad 生态发展这么快"。
  3. 用户会看到什么：熟悉的 DApp 类型（Swap、质押等）在 Monad 上也能找到对应版本。
  4. 哪些动作会改变状态：本章为概念章节，不涉及具体操作。
  5. 操作前检查什么：操作前确认钱包连接的网络确实是 Monad，而不是以太坊或其他链。

**挑战**（判断题 ×1）

- 场景：你发现隔壁"以太坊农场"的种植工具，好像稍微改改就能直接在 Monad 农场用。
- 题目：Monad 兼容 EVM，意味着原本部署在以太坊上的智能合约，通常只需少量甚至无需修改就能部署到 Monad 上。
- 答案：正确
- 答对反馈："对，这也是为什么 Monad 农场能这么快就热闹起来——很多好用的工具直接就能搬过来用。"
- 答错反馈："再想想：如果两条链的底层规则差不多，那开发者是不是就不用从零重写代码了？"

### 3.2 第 2 章：RPC、区块与浏览器（熟练/巩固）

- **章节目标**：学完你会用区块浏览器查一笔交易，并知道 Gas 不能说明交易是否成功。
- **正文**（约 240 字）：
  区块浏览器是查看链上一切公开信息的窗口——每个网络都有自己独立的浏览器，Monad 上的交易要用 Monad 对应的浏览器查询，不能拿以太坊浏览器去查。想确认一笔交易到底成功没有，不能只看 Gas 花了多少钱，Gas 只能说明"花费了多少"，真正判断成败的依据是交易回执（Receipt）里的状态字段。区块高度则代表账本增长到了哪一页，越新的区块高度越靠后。
- **关键术语**：区块浏览器、交易回执、区块高度。
- **例子**：把交易哈希粘贴进 Monad 区块浏览器搜索框，就能看到这笔交易的完整状态和详情。
- **风险/注意事项**：查交易时认准官方/可信的区块浏览器地址，避免打开仿冒页面。
- **知识卡**：
  1. 是什么：区块浏览器是查询链上公开数据的窗口，回执是判断交易成败的依据。
  2. 为什么要知道：能自己核实一笔交易而不是只听别人说。
  3. 用户会看到什么：交易哈希、状态字段（成功/失败）、区块高度、Gas 消耗。
  4. 哪些动作会改变状态：查询是读取操作，不改变任何状态。
  5. 操作前检查什么：确认打开的是官方区块浏览器地址，而不是仿冒页面。

**挑战**（两项选择 ×1 + 简单排序 ×1）

**两项选择**
- 场景：你想确认一笔货有没有真的送到。
- 题目：想知道一笔 Monad 交易到底成功了没有，该看什么？
  - A. 这趟运费花了多少（Gas 价格）　　B. 送货回执上的状态（交易回执）
- 答案：B
- 答对反馈："运费只能说明花了多少钱，回执才能告诉你东西到底送到没有。"
- 答错反馈："再想想：花了钱和东西送没送到，是一回事吗？"

**简单排序**
- 场景：你想弄清楚朋友发给你的那笔交易到底是什么情况。
- 题目：把用区块浏览器查询一笔交易的步骤排个顺序：① 打开 Monad 区块浏览器 ② 复制这笔交易的哈希 ③ 粘贴进搜索框查询 ④ 查看交易状态和区块高度
- 答案：② → ① → ③ → ④
- 提示 1："你得先有点线索（哈希）才能去查，对不对？"
- 提示 2："线索准备好之后，是先打开浏览器，还是先搜索？"
- 答对反馈："对，这就是核实一笔交易最基本的步骤。"

### 3.3 第 3 章：测试环境与资产安全（认真收尾 · 严肃模式）

> 本章为安全章节，Agent 引导语固定为："这一步涉及账户或资产安全，我陪你认真确认一遍。"

- **章节目标**：学完你会分清测试网和主网、能识别围绕测试资产展开的骗局。
- **正文**（约 230 字）：
  测试网络上的资产（包括测试用的 MON）本身没有真实价值，唯一作用是让你在不花真钱的情况下练习操作。任何围绕"用真钱换测试币"或"测试币换真钱"展开的交易，背后往往是诈骗话术——正常情况下不会有人愿意为没有真实价值的东西付真钱。另外，操作前一定要核对自己连接的网络是不是预期的那一个，陌生网络的切换请求也是常见的风险来源之一。
- **关键术语**：测试网、主网、网络核对。
- **例子**：朋友说想用 100 元人民币"收购"你测试网里的 1000 个测试 MON，这类交易应该被直接拒绝。
- **风险/注意事项**：本章是全课程安全底线之一，答错时不使用轻松文案。
- **知识卡**：
  1. 是什么：测试网资产没有真实价值，仅用于练习。
  2. 为什么要知道：能识别"测试币变现"类骗局。
  3. 用户会看到什么：钱包界面通常会标注当前所在网络（测试网/主网）。
  4. 哪些动作会改变状态：切换到陌生网络后进行的操作可能涉及真实资产风险。
  5. 操作前检查什么：确认当前网络是否符合预期，拒绝任何"测试币换真钱"的交易请求。

**挑战**（风险场景判断 ×2）

**第 1 题**
- 题目：朋友想用 100 元人民币"收购"你测试网钱包里的 1000 个测试 MON，你应该？
  - A. 可以卖，反正是测试代币，不亏　　B. 测试网资产没有真实价值，这类交易背后往往是诈骗话术，不建议参与
- 答案：B
- 反馈：答对——"守住了，练习的东西就是拿来练手的，一旦有人想用真钱换，要多留个心眼。"答错——"测试资产本身没有真实价值，正常情况下不会有人愿意为它付真钱。这类交易背后几乎都是诈骗话术，不要参与。"

**第 2 题**
- 题目：钱包突然弹出提示，要求你切换到一个从没见过的陌生网络才能"完成一笔操作"，你应该？
  - A. 先切换过去再说，操作完再切回来　　B. 先核实这个网络是什么、为什么需要切换，不明来源的网络请求不要直接同意
- 答案：B
- 反馈：答对——"对，网络切换请求看起来只是个技术步骤，但背后可能是资产被转移的第一步，先核实没错。"答错——"陌生网络切换请求是常见的风险来源之一，不清楚来源和目的前，不要直接同意切换。"

最终验证要点（对应 v3.5 §5.3）：能解释钱包账户与网络的关系；能说明如何在区块浏览器中查找交易；能区分测试环境练习和真实资产操作。

## 4. 智能合约课程（完整 3 章）

**学习目标**：理解智能合约状态、函数、ABI、事件和交易回执。

### 4.1 第 1 章：合约、状态与函数（认识/破冰）

- **章节目标**：学完你会知道，智能合约是什么、部署之后能不能被随意改动。
- **正文**（约 210 字）：
  智能合约可以理解为部署在链上、按固定规则自动执行的程序。它有自己的"状态"（比如记录了谁存了多少钱），也有可以被调用的"函数"（比如存款、取款、查询余额）。合约一旦部署，代码本身默认不能被随意修改——这也是为什么智能合约常被认为"规则透明、不能被人为篡改"，同时也意味着如果代码本身有漏洞，通常无法事后偷偷改掉，这也是安全审计如此重要的原因。
- **关键术语**：智能合约、状态、函数。
- **例子**：一个存款合约的"状态"记录着每个地址存了多少钱，调用它的"存款函数"会改变这个状态。
- **风险/注意事项**：合约代码公开可查，但普通用户不需要自己读代码——后面章节会讲怎么通过回执判断结果。
- **知识卡**：
  1. 是什么：智能合约是部署在链上、按固定规则自动执行的程序。
  2. 为什么要知道：理解"规则写死在代码里"是链上应用和普通网站最大的区别。
  3. 用户会看到什么：与合约交互的界面（如存款、兑换按钮），背后调用的就是合约函数。
  4. 哪些动作会改变状态：调用写入类函数（如存款、转账）会改变合约记录的状态。
  5. 操作前检查什么：本章为概念章节，重点在建立"合约=自动执行的规则"这个认知。

**挑战**（判断题 ×1）

- 场景：仓库的自动分拣机器一旦设定好规则，就会一直按这个规则运转。
- 题目：智能合约部署后，代码本身默认不能被随意修改。
- 答案：正确
- 答对反馈："对，规则写死在代码里，这也是智能合约'公平透明'的来源。"
- 答错反馈："再想想：如果合约代码可以被人偷偷改，那大家还敢把资产放进去吗？"

---

### 4.2 第 2 章：读取、写入与 ABI（熟练/巩固）

- **章节目标**：学完你会知道，只读函数为什么不用付 Gas、ABI 到底是干嘛的。
- **正文**（约 240 字）：
  合约里的函数分两类：标记为 view / pure 的只读函数，只是在本地节点上查询当前状态，不会改变链上数据，所以调用它不需要广播交易，也不用付 Gas；而会改变合约状态的写入函数，则需要签名、广播、上链，会消耗 Gas。前端和钱包要知道"怎么调用合约的某个函数、怎么解析它返回的数据"，靠的是 ABI——可以把 ABI 理解成合约的说明书，没有它，前端根本不知道该怎么和合约"对话"。
- **关键术语**：只读函数、写入函数、ABI。
- **例子**：查询某个地址存了多少钱是只读函数调用，不花 Gas；往里存钱是写入函数调用，需要签名并花 Gas。
- **风险/注意事项**：调用写入函数前，留意界面展示的参数是否是你真正想操作的内容。
- **知识卡**：
  1. 是什么：ABI 是合约与前端应用之间"怎么对话"的说明书。
  2. 为什么要知道：理解界面背后其实是在按 ABI 规则调用合约函数。
  3. 用户会看到什么：只读查询即时返回结果；写入调用会弹出签名请求。
  4. 哪些动作会改变状态：只有写入函数调用会改变合约记录的状态。
  5. 操作前检查什么：写入操作前核对参数（金额、地址等）是否正确。

**挑战**（两项选择 ×1 + 简单排序 ×1）

**两项选择**
- 场景：仓库的说明书上有些按钮只能看，有些能真的动手操作。
- 题目：调用合约里标记为 view / pure 的只读函数，通常需要付 Gas 吗？
  - A. 需要　　B. 不需要
- 答案：B
- 答对反馈："对，只是看看说明书，不用花钱，只有真的动手改东西才要花 Gas。"
- 答错反馈："再想想：只是查询，链上的数据有没有被真的改动？"

**简单排序**
- 场景：你想往一个存款合约里存点东西。
- 题目：把调用一个写入函数（如"存款"）的流程排个顺序：① 合约执行并更新状态 ② 用户在前端输入参数并点击调用 ③ 钱包弹出签名请求 ④ 交易广播上链
- 答案：② → ③ → ④ → ①
- 提示 1："你总得先告诉前端你要做什么、存多少，是不是？"
- 提示 2："输入完之后，是先签字确认，还是先广播出去？"
- 答对反馈："对，这就是前端、钱包和合约配合完成一次写入操作的完整过程。"

---

### 4.3 第 3 章：回执、事件与权限风险（认真收尾 · 严肃模式）

> 本章为安全章节，Agent 引导语固定为："这一步涉及账户或资产安全，我陪你认真确认一遍。"

- **章节目标**：学完你会知道，怎么通过回执判断交易是否成功、什么样的授权请求要提高警惕。
- **正文**（约 230 字）：
  一笔与合约的交互是否真正成功，不能只看前端界面的提示文字，要看链上交易回执里的状态字段——这是唯一可信的依据。另外要特别警惕"无限额度批准"这类授权请求：一旦同意，对方合约未来可能在你不知情的情况下转走全部被授权的资产。"方便以后操作"往往正是钓鱼合约用来降低警惕的说法，遇到陌生 DApp 的这类请求，应该先核实合约来源再决定。
- **关键术语**：交易回执、事件、无限额度批准。
- **例子**：一个陌生 DApp 弹窗请求"无限额度批准"你的 USDC，这类请求需要先核实来源。
- **风险/注意事项**：本章是全课程安全底线之一，答错时不使用轻松文案。
- **知识卡**：
  1. 是什么：回执是判断交易成败的唯一可信依据；无限额度批准是一类高风险授权。
  2. 为什么要知道：这是链上交互中最常见的两类"被误导"风险。
  3. 用户会看到什么：钱包弹出的授权额度请求，通常显示为具体数字或"无限"。
  4. 哪些动作会改变状态：同意无限额度批准后，对方合约可在未来任意时间转走被授权资产，无需再次确认。
  5. 操作前检查什么：授权前确认额度是否合理、来源是否可信；交易后以链上回执状态为准，不轻信前端文案。

**挑战**（风险场景判断 ×2）

**第 1 题**
- 题目：一个陌生 DApp 弹窗请求"无限额度批准"你的 USDC，你应该？
  - A. 直接同意，方便以后操作　　B. 谨慎处理，这意味着对方以后可能不打招呼就拿走你所有授权的资产，需先核实来源
- 答案：B
- 反馈：答对——"守住了，无限额度批准这件事，值得每次都认真对待。"答错——"'方便'两个字，恰恰是很多风险合约用来让人放松警惕的说法。无限额度批准意味着对方未来可以不经过你直接转走资产，务必先核实来源。"

**第 2 题**
- 题目：一个 DApp 提示"交易已完成"，但你还没在区块浏览器上看到回执确认，对方却催促你赶紧进行下一步操作，你应该？
  - A. 相信提示文字，直接继续下一步　　B. 先自己核实链上回执状态，确认真正成功后再继续
- 答案：B
- 反馈：答对——"对，前端提示文字可以造假，链上回执不会。先核实再继续，是对的。"答错——"界面上的文字提示不能作为交易成功的依据，真正可信的只有链上回执状态。催促操作本身也是一种常见的施压信号。"

最终验证要点（对应 v3.5 §5.4）：能解释读取函数和写入函数的区别；能说明 ABI 的作用；能通过回执判断交易是否成功。

## 5. Agent 标准化提问题库（三门课程，每门 3 题，共 9 题）

字段结构固定为：问题文本 / 必须包含的知识要点 / 允许的等价表达 / 错误或危险表达 / 第一次提示 / 第二次提示 / 通过条件（对应 v3.5 §9.2）。

### 5.1 Web3 通识

**问题 1**
- 问题文本：如果你不小心把钱包地址发给了陌生人，会有安全问题吗？聊聊你的想法。
- 知识要点：地址是公开信息；分享地址本身不会导致资产被盗；真正需要保密的是私钥/助记词。
- 允许的等价表达："地址是公开的""别人查得到但拿不走我的钱""只要不给助记词就没事"。
- 错误或危险表达：认为地址泄露=资产不安全；混淆地址与私钥的保密级别。
- 第一次提示：地址更像是门牌号，还是钥匙？
- 第二次提示：别人知道你家门牌号，能直接进你家搬东西吗？
- 通过条件：用户能明确说出"地址公开无风险，私钥/助记词才需要保密"。

**问题 2**
- 问题文本：为什么只是看看余额不用签字，但转账要签字，这中间的区别在哪？
- 知识要点：查询是读取操作，不改变链上状态；转账是写入操作，会改变链上状态，需要用户授权确认。
- 允许的等价表达："查余额只是看看""转账是真的动了钱，所以要签字确认"。
- 错误或危险表达：认为所有链上操作都一样需要签名，或认为签名只是走个形式。
- 第一次提示：签字的意思是"我同意让这件事发生"，那什么事需要被同意？
- 第二次提示：看一眼余额，链上的数字变了吗？转账之后呢？
- 通过条件：用户能区分"读取不改变状态"和"写入需要授权"这两类操作。

**问题 3**
- 问题文本：如果有人说"官方活动，输入助记词领取空投"，你会怎么判断？
- 知识要点：任何正规渠道都不会索要助记词/私钥；这是典型钓鱼话术。
- 允许的等价表达："不管说得多正式，要助记词就是骗子""官方不会问我要助记词"。
- 错误或危险表达：认为"看起来正规"或"金额不大"就可以尝试。
- 第一次提示：助记词等于你钱包的全部控制权，什么样的"活动"值得你交出这个？
- 第二次提示：如果真是官方活动，它需要知道你的助记词才能给你发东西吗？
- 通过条件：用户明确表示不会提供助记词，并能说出"索要助记词=风险信号"这一判断依据。

### 5.2 Monad 基础

**问题 1**
- 问题文本：为什么原本在以太坊上的合约能很快部署到 Monad 上？
- 知识要点：Monad 兼容 EVM，开发工具和代码可复用；但不代表两条链完全一样，网络、RPC 需要分别核对。
- 允许的等价表达："因为兼容 EVM，代码基本能直接搬过来""底层规则差不多，改一改就能用"。
- 错误或危险表达：认为兼容 EVM 就等于"两条链是同一条链"，可以混用网络设置。
- 第一次提示：想想"兼容"这个词，是指底层规则相似，还是完全变成同一条链？
- 第二次提示：即使代码能复用，网络地址会不会也是同一个？
- 通过条件：用户能说出"EVM 兼容带来开发便利，但网络仍然独立，需要分别核对"。

**问题 2**
- 问题文本：怎么确认一笔 Monad 交易到底成功了没有？
- 知识要点：通过区块浏览器查看交易回执的状态字段判断，Gas 消耗不能说明是否成功。
- 允许的等价表达："去浏览器查回执状态""光看花了多少 Gas 说明不了成没成功"。
- 错误或危险表达：认为 Gas 花出去了就等于交易成功。
- 第一次提示：花钱和东西送到了，是一回事吗？
- 第二次提示：想确认结果，该看运费单还是签收回执？
- 通过条件：用户能说出"依据交易回执的状态字段判断成败，而不是 Gas"。

**问题 3**
- 问题文本：朋友想用真钱换你测试网里的 MON，你会怎么判断？
- 知识要点：测试网资产没有真实价值，这类交易背后往往是诈骗话术。
- 允许的等价表达："测试币不值钱，这种交易很可疑""练习用的东西没人会真花钱买"。
- 错误或危险表达：认为"反正是测试币，卖了也不亏"，可以尝试交易。
- 第一次提示：测试网资产本来是用来干嘛的？
- 第二次提示：如果一个东西本来没有真实价值，为什么会有人愿意花真钱买？
- 通过条件：用户明确表示不会参与这类交易，并说出"测试资产无真实价值，涉及真钱要警惕"。

### 5.3 智能合约

**问题 1**
- 问题文本：只是查看合约里的公开信息（只读函数），需要花 Gas 吗？为什么？
- 知识要点：只读函数只在本地查询当前状态，不改变链上数据，不需要广播交易，所以不花 Gas。
- 允许的等价表达："只是看看，不用花钱""没有真的改动链上的东西，所以不用付 Gas"。
- 错误或危险表达：认为所有合约调用都要花 Gas。
- 第一次提示：只读函数有没有真的改变链上记录的东西？
- 第二次提示：花 Gas 的前提，是不是要把这次操作广播给全网？
- 通过条件：用户能说出"只读不改变状态，不需要广播，所以不花 Gas"。

**问题 2**
- 问题文本：ABI 是干什么用的，为什么前端需要它？
- 知识要点：ABI 是合约与前端应用之间的说明书，规定了如何编码调用合约函数、如何解析返回的数据。
- 允许的等价表达："ABI 就是合约的说明书，告诉前端怎么跟合约对话""没有它前端不知道怎么调用合约"。
- 错误或危险表达：认为 ABI 是用来加密数据或防止合约被攻击的。
- 第一次提示：前端要调用合约的某个功能，得先知道这个功能长什么样，对吧？
- 第二次提示：这份"说明书"里写的是安全规则，还是调用格式？
- 通过条件：用户能说出"ABI 规定了前端如何调用合约、如何解析返回结果"。

**问题 3**
- 问题文本：一个陌生 DApp 弹窗请求"无限额度批准"你的资产，你会怎么处理？
- 知识要点：谨慎处理，无限额度批准意味着对方未来可能不打招呼就转走全部授权资产，需先核实合约来源。
- 允许的等价表达："这个挺危险的，得先查一下这个合约是谁的""不能图方便就随便同意"。
- 错误或危险表达：认为无限额度批准只是"方便以后操作"，没有额外风险。
- 第一次提示："方便以后操作"这句话，是在提醒你什么风险，还是在让你放松警惕？
- 第二次提示：如果额度是无限的，未来这份权限还需要你再次同意吗？
- 通过条件：用户能说出"无限额度批准=未来可无提示转走资产，需先核实来源"。
