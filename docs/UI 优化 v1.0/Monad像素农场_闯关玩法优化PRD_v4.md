## 1. 设计原则（延续并细化 v3.5 §0.2 的产品公式）

- **学习结果必须可验证，学习过程可以很温柔** —— 沿用 v3.5 总纲，不改变。
- **每个农场活动对应一个明确的知识域**，不是三门课程各自平铺相似难度的判断题，而是种植、钓鱼、兑换分别承担不同深度、不同性质的学习内容（见第 2 节）。
- **"链上实操"优先于"链上展示"**：现有设计里，gas/耗时/回执大多是系统展示给玩家看的结果；本次优化要增加玩家**主动操作、主动核验**的环节，如自己去对交易哈希、自己去浏览器查回执。
- **知识密度通过"绑定真实数据"提升，而不是通过增加题量或加长文字提升**：一道题如果换个链名字还成立，说明它不够 Monad 专属，需要重写或替换为绑定具体机制/数字/协议名的题目。
- **陪伴式语气不等于内容浅**：v3.5 已经把语气和难度解耦（语气可以软，判定标准不能降），本文档延续这个原则，重点加深的是判定标准里"必须包含的知识要点"，而不是把语气改严肃。

## 2. 知识域与农场活动映射（核心架构调整）

v3.5 现状：三门课程（Web3 通识 / Monad 基础 / 智能合约）各自内部走"认识→熟练→认真收尾"的难度曲线，但知识内容彼此独立，和"种植"这个唯一的农场动作绑定，钓鱼、兑换等其他农场活动没有承担学习功能，显得和主题脱节。

优化方向：把**知识域拆分到不同的农场活动上**，形成"活动即课程模块"的结构，而不是"课程模块套壳成活动"：

| 农场活动 | 知识域 | 内容深度定位 | 对应课程章节（沿用 v3.5 编号） |
|---|---|---|---|
| 种植 / 收获 | Web3 通识基础：账户、地址、读写操作、签名 | 保留现有难度，作为整个学习路径的入口 | Web3 通识 第 1～2 章 |
| **钓鱼**（新增学习功能） | 交易生命周期、Gas、Pending / 确认机制，绑定玩家真实操作数据出题 | 从"知道流程"升级到"能核验自己刚发生的这笔交易" | 对应 Web3 通识 第 2 章的排序题 + Monad 基础第 2 章，建议合并重构，见第 3、5 节 |
| 小屋装饰 / 兑换商店 | Monad 技术特性 + 生态协议：并行执行、MonadBFT、EVM 兼容边界、生态协议（如 Kuru、aPriori 等，需与团队确认当前生态实际接入的协议名） | 这是目前题库里**最薄弱**的一环，几乎没有 Monad 专属内容，本文档重点补强 | 对应 Monad 基础第 1 章，建议扩展 |
| 风险场景判断（贯穿三门课程收尾章） | 安全知识，私钥/助记词/授权风险 | 维持现有深度和严肃语气，不做改动 | 三门课程各自第 3 章 |

这样调整后，递进性不再是"每门课程内部走一次低-中-高"，而是变成**玩家玩到哪个农场活动，就自然进入对应深度和性质的学习内容**——种植负责打基础，钓鱼负责练手感（链上实操），装饰/兑换负责讲清楚"这是 Monad，不是随便一条链"，风险关卡负责兜底安全。

## 3. 钓鱼玩法设计：不是"钓鱼时答题"，是"钓鱼本身就是在练习"

### 3.1 设计前提

现有钓鱼机制（若已在 Demo 中实现基础版本）通常是：蓄力抛竿 → 等待上钩 → 点击/QTE → 获得渔获。这个节奏和"发起交易 → pending → 确认"高度同构，适合直接复用，不需要额外发明一套新机制，只需要把每个动作节点接上真实的链上语义。

### 3.2 具体流程设计

| 钓鱼动作 | 现有反馈（推测/复用） | 优化后的链上语义绑定 | 教学作用 |
|---|---|---|---|
| 抛竿 | 播放抛竿动画 | 这是一次真实的低成本链上交易（读取或轻量写入均可，需工程侧确认最终实现），抛竿瞬间即广播 | 建立"我的每个操作都是一笔交易"的直觉，比种植更高频、更低心理门槛 |
| 浮标等待 | 等待动效 | 浮标状态与交易 pending 状态绑定，玩家可以点击浮标查看"当前这笔交易还在等待确认"的实时提示，而不是纯装饰动画 | 把原本只是气氛渲染的等待动效，变成一个可交互、可核验的信息面板 |
| 咬钩 | 提示上钩、QTE | 交易确认瞬间触发，此时展示这笔交易的真实数据：区块高度、Gas 消耗、确认耗时 | 把"结果展示"从事后弹一次性卡片，变成和玩法动作本身绑定的即时反馈 |
| 收鱼入篓 | 直接收进背包 | **新增一步核验动作**：从两个候选数字/哈希片段中选出真正属于这笔交易的那一个，选对才能收鱼；不强制学习动机，包装成"确认这条鱼真的是你钓的" | 直接回应"缺少提交交易哈希类实操"的反馈，且是低门槛的轻量交互，不是要求玩家手打一串哈希 |
| 渔获入图鉴 | 无（新增） | 每种鱼对应一个 Monad 概念或协议，见 3.3 | 把知识库从"任务附属品"变成"玩家主动想收集的东西" |

核验动作的交互建议（供工程评估工作量）：钓上鱼后弹出小卡片，展示这笔交易的哈希后 6 位和另一个"干扰哈希"后 6 位，玩家点选正确的那个即可，答错不惩罚、只是提示"再看一眼交易详情"，不使用倒计时或失败次数限制，延续 v3.5 §7.2 的通用规则（不通过晦涩措辞或倒计时制造难度）。

### 3.3 鱼类图鉴：知识库的载体

- 每种鱼绑定一个 Monad 概念/协议/技术特性，图鉴条目结构复用 v3.5 §6.3 知识卡的五问结构（是什么 / 为什么要知道 / 会看到什么 / 哪些动作会改变状态 / 操作前检查什么），保持内容体系一致，不新增格式。
- 鱼的外观/习性可以呼应概念本身，示例（具体鱼名、数值待美术与技术团队核实后确定，此处仅示意设计逻辑）：

| 鱼类示例 | 绑定概念 | 习性设计意图 |
|---|---|---|
| 并行鱼 | Monad 并行执行机制 | 总是成群出现，一次上钩多条，呼应"多笔交易并行处理" |
| 速交鱼 | 出块速度 / 交易确认速度 | 咬钩极快，几乎不用等，呼应 Monad 的高吞吐特性（具体出块时间由团队核实官方最新数据后写入文案，避免用不准确的旧数字） |
| 兼容鱼 | EVM 兼容性 | 长得和"以太坊鱼"很像，但细看有 Monad 特有花纹，呼应"兼容但不是同一条链" |
| 协议鱼（可拆分多种） | 生态内具体协议（Swap 类、质押类等，具体协议名需团队核实当前 Monad 生态实际可对接的项目，避免写错或写入已下线项目） | 每种协议鱼对应一个真实存在的生态项目，钓上后图鉴内容直接科普"这个协议是做什么的" |

- 稀有鱼与 v3.5 §4.3（链上足迹解锁内容）机制打通：钱包在 Monad 生态有真实历史交互（如用过某协议、持有某类资产）才能解锁对应稀有鱼，不需要新建一套解锁系统，复用现有的"链上足迹检测"逻辑，只是把解锁对象从"隐藏 NPC/作物"扩展到"隐藏鱼类"。

### 3.4 与三门课程的衔接方式

钓鱼不替代任何一门课程，而是作为**Web3 通识课程"读取/签名/交易"章节的实操延伸**：理论章节讲清楚"签名前后交易经历了什么阶段"，钓鱼提供一个可以反复练习、无学习压力的场所去亲手体验这个过程。建议在该章节结尾增加一句引导："去池塘边钓条鱼，亲自感受一下这个过程"，作为可选的实践入口，不计入课程通过条件，避免打乱 v3.5 已冻结的状态机。

## 4. 装饰 / 兑换商店：Monad 专属知识的主战场

现有题库里"Monad 基础"课程的内容仍偏通用（EVM 兼容、浏览器查询、测试网风险），这些知识点正确但不够"扎心"——换成任何 EVM 兼容链的教程也成立。建议把**并行执行、MonadBFT 共识、Monad 的具体性能定位**这类真正差异化的内容，放到装饰/兑换商店场景里讲：

- 兑换前解释弹窗（v3.0/v3.5 已有设计）可以顺带植入一句 Monad 专属机制说明，例如兑换发生时提示"这笔兑换和你之前的操作可以在 Monad 上并行处理，不需要排队等待前一笔完成"，把并行执行从抽象概念变成玩家能感知到的体验差异。
- 装饰道具的解锁条件可以绑定"是否理解某个 Monad 特性"，比如解锁一件带有 Monad 品牌元素的装饰前，触发一次简短的 Agent 对话，而不是判断题（题型不新增，用已有的 Agent 对话形式，只是换个触发场景）。

> 待团队确认：本节涉及具体技术数字（如并行执行的性能表现、共识出块时间等），需要技术背景的两位成员核实当前 Monad 官方最新口径后再落地文案，避免使用过时或不准确的数字，这类专属知识点如果写错，反而会被评委当场纠正，风险比"内容简单"更大。

## 5. 题库改造规范

### 5.1 Monad 专属化检验标准

写完每道题后，用这个问题自检：**把"Monad"替换成任意一条 EVM 兼容链的名字，这道题是否依然成立？** 如果成立，说明题目不够专属，需要以下方式之一处理：

1. 换成绑定具体数字/机制的表述（如具体的 Gas 数量级、具体的确认速度感受、具体的协议名称）；
2. 换成绑定玩家刚刚在游戏内产生的真实操作数据（钓鱼、种植、兑换时产生的哈希、区块高度、耗时），题目直接引用"你刚才这笔操作"，天然具备专属性，无法套用到别的场景；
3. 如果确实是通用 Web3 基础知识（如私钥不能分享），保留但不再作为"体现 Monad 特色"的证据，明确归入"通识基础"分层，不占用"Monad 基础"课程的核心题量。

### 5.2 题型不变，但增加"绑定真实数据"的出题方式

延续 v3.5 §8.1 固定的四种题型（判断题、两项选择、简单排序、风险场景判断），不新增题型，但新增一种出题素材来源：

> **系统自动取材题**：题干由玩家刚完成的操作数据动态生成，例如"你刚才这笔交易在第几个区块被确认？"配合玩家自己在结算卡片上看到过的数字作为选项，或者更轻量地："这笔交易花的 Gas，大概是以太坊上同类操作的哪个量级？"（选项设计为数量级对比，而非要求记住精确数字）。

这类题目工程实现成本略高于静态题库（需要读取玩家本次操作的结果作为题目参数），建议先在钓鱼场景试点（因为钓鱼本身高频、单次操作轻量，適合反复出题），再评估是否推广到种植和兑换场景。

### 5.3 示例：Monad 基础课程题目改造对照

| 现有题目（细化 PRD 已有内容） | 问题 | 改造方向示例 |
|---|---|---|
| "Monad 兼容 EVM，意味着原本部署在以太坊上的智能合约通常只需少量修改就能部署到 Monad 上"（判断题） | 换成任何 EVM 兼容链都成立，不够专属 | 保留作为通识基础题（不占 Monad 专属题量），新增一道绑定并行执行或共识机制的题目作为该章节的"体现 Monad 差异化"的核心题 |
| "判断一笔 Monad 交易是否成功，应该看 Gas 价格还是交易回执状态字段"（两项选择） | 这个判断逻辑适用于任何链，不是 Monad 专属 | 保留（因为它教的是"如何核验"这个通用但重要的能力），但建议改造成"系统自动取材题"：直接让玩家去查自己刚才那笔操作的真实回执状态，而不是选择题 |

## 6. Agent 验证增强

### 6.1 现状与问题

v3.5 §9.2 和《闯关模块细化 PRD》第 5 节已经设计了每门课程 3 道 Agent 标准化提问，字段结构（知识要点/等价表达/危险表达/两次提示/通过条件）比较完整，问题不在"有没有 Agent"，而在**Agent 验证的问题目前都是固定文本，和玩家的具体游玩过程无关**，本质上还是"背好答案的对话式选择题"，不是评委反馈里期待的"真正的验证"。

### 6.2 优化方向

- **引入至少 1 道"引用玩家真实操作数据"的 Agent 问题**，替换或补充到每门课程的 3 题标准问题里，例如："你刚才在池塘边钓到的那条鱼，交易确认花了多久？这说明 Monad 在处理交易时有什么特点？"——这道题没有固定文本答案，Agent 需要先读取玩家本次操作的真实数据，再据此追问和判定，判定标准从"是否说出关键词"升级为"是否能把具体数据和背后的机制说清楚"。
- **风险类章节的 Agent 验证维持现有严肃模式不变**，本次优化不涉及安全内容的验证方式，避免在"最不能出错"的地方引入不确定性。
- **Agent 追问深度分级**：普通知识点保留现有的"两次提示"机制；涉及真实操作数据的题目，建议 Agent 追问时能进一步问"如果这笔操作换一种方式，结果会有什么不同"，制造真正的追问感，而不是提示走向标准答案后就结束。

> 待技术团队评估：Agent 读取玩家实时操作数据（哈希、区块高度、耗时）作为对话上下文，需要后端把这些数据结构化传给 Agent 服务，工程量高于纯文本题库，建议作为 P1 而非黑客松 MVP 必须项，具体排期见第 9 节。

## 7. 图鉴系统与学完之后的留存设计

延续你（提出者本人）在方案 B 中"学完之后农场还在"的立场，本节把钓鱼图鉴具体落成一个可执行的留存机制，呼应 v3.5 §24.3 已经把图鉴列为后续版本、但本文档建议提前规划其数据结构，方便和 MVP 阶段的钓鱼功能共用底层设计：

- 三门课程学完之后，游戏内容不会"结束"，图鉴收集没有终点——已解锁的鱼类图鉴持续可查看、可回顾，未解锁的稀有鱼继续留有"链上足迹解锁"的悬念（比如后续在生态里用了新协议，回来钓鱼可能解锁新鱼）。
- 图鉴页面复用 v3.5 已有的"成就档案"入口（v3.5 §1.4、§6.3 知识卡入口已列出"个人学习档案"），不新增页面结构，只是新增图鉴作为档案的一个子模块。
- 这个设计不需要在黑客松现场完整实现，可以像 v3.5 附录里已有的"经营系统留待 Roadmap"的处理方式一样，只需要在演示脚本收尾和路演 PPT 里说清楚这条设计逻辑，工程量极低。

## 8. 验收标准

- [ ] 三门课程的知识内容按第 2 节完成"活动-知识域"重新映射，种植/钓鱼/装饰兑换分别承担不同性质的学习内容。

- [ ] 演示脚本更新，加入钓鱼实操核验环节作为"链上实操"的现场展示重点。

## 9. 落地优先级建议（供团队讨论排期）

| 优先级 | 内容 | 理由 |
|---|---|---|
| P0（黑客松 MVP 应尽量做） | 钓鱼流程的核验交互（3.2）、题库 Monad 专属化改造（5.1、5.3） | 直接回应"缺链上实操"和"关联性弱"两条最硬的反馈，工程量相对可控 |
| P1（时间富余再做） | 鱼类图鉴系统（3.3）、Agent 读取真实操作数据验证（6.2） | 价值高但依赖后端数据结构改造，风险在于可能挤占 P0 的开发时间 |
| P2（写入 Roadmap，现场不实现） | 稀有鱼与链上足迹解锁的完整打通（3.3）、装饰/兑换的并行执行体验化（第 4 节） | 概念验证价值大于现场演示价值，且涉及需要团队技术成员核实的专属数字，风险较高，不适合临场赶工 |
